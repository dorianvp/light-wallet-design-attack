### 1. The linked thread: zcash/zcash issue #288 "Detection Keys" (Oct 2015 – Apr 2021)
https://github.com/zcash/zcash/issues/288 (repo archived read-only Jul 19, 2026). The article links specifically to Daira Hopwood's comment https://github.com/zcash/zcash/issues/288#issuecomment-658348272. Relevant content, verified by fetching the issue:

- **nathan-at-least (Oct 6, 2015)** defines the feature ladder still used in discussions: Base Case → MC → MUC → PARC → **PALC** (detector can link a *known* address to a detection identifier, but not recover addresses) → **AC** (address confidentiality) → **PIRU** (detector cannot even tell two received txs go to the same wallet) → Full Node. Hornby's performance-optimized wallet sits between PALC and AC; his privacy-optimized wallet is Full-Node-equivalent. Issue labels include `M-requires-zip`, `SPV support` — it was never resolved into a ZIP.
- **gtank (Mar 14, 2019)** https://github.com/zcash/zcash/issues/288#issuecomment-472912826 — three approaches: (1) extra key encrypting a "detection tag" (prior art: Sapling `ovk`/in-band secrets), (2) block-level accumulators (Camenisch accumulators, Facebook LtHash; "possibly encrypted bloom filters, but full PIR is impractical"), (3) designated-verifier proofs / conditionally blind signatures (cites https://eprint.iacr.org/2017/682).
- **gtank (Mar 15, 2019)** https://github.com/zcash/zcash/issues/288#issuecomment-473311130 — **first published break in this space**: "There's an attack if the detection keys are derivable without any per-transaction randomness, which is that anyone who knows a payment address can derive the detection key for that address and see when other payments are going to it." This rules out any symmetric accumulator/sublinear approach with a static per-address key — the reason Hornby's 2023 design derives tags through `K_TT = H(s)` *plus* per-epoch `e` *plus* blinding of `G_r` from the server.
- **gmale (Nov 8, 2019)** https://github.com/zcash/zcash/issues/288#issuecomment-551955431 — quotes Daira (2019): "In order for this to not break privacy, it has to be the case that each user of the service provider can't see which outputs are directed to other users of that provider. The difficult issue that I haven't solved yet is how the provider … then distributes them only to the right users without leaking information about their other users … maybe you need two layers of detection keys. that's clearly possible but results in quite long addresses." Also Brad (ECC): wallet vendors resist doing server-side key management.
- **daira (Jul 14, 2020)** https://github.com/zcash/zcash/issues/288#issuecomment-658348272 — **the "Daira Hopwood detection key design" the article says could replace the whole `K_TT`/address-secrecy machinery**: encrypt the note plaintext to `(d, pkd)` as usual (inner), then re-encrypt `(inner ciphertext, d, rseed_outer)` to a *diversified detection key* `(d, dkd)` where `dkd = [dsk]GH(d)`, `esk_outer = H(rseed_outer)` (ZIP 212-style check for the same_faustian-attack reason — see https://zips.z.cash/zip-0212). The detector knows `dsk`, decrypts the outer layer, and uses `d` to route to the right user **without learning other users' data**; the *user* never learns `dsk`, so a leak of the user's data doesn't compromise other users. Address = `(d, dkd, pkd)` (75 bytes raw; 96 if re-randomizable via `g_d`). This is exactly the "two layers of detection keys" idea from 2019, now concrete.
- **daira (Jul 14, 2020, follow-up)** https://github.com/zcash/zcash/issues/288#issuecomment-658354096 — self-critique: "A potential problem with the above design is that the user *has to* rely on the detector; it can't detect payments to that address itself if it stops trusting the detector. It is probably better to use independent ciphertexts rather than nested encryption." This is the known trade-off Hornby's 2023 design inherits in different form (his Option-2 wallets keep trial decryption of the current epoch only).
- **gtank (May 9, 2019)** https://github.com/zcash/zcash/issues/288#issuecomment-491078883 — designated-verifier Schnorr "detection signature" using RedDSA bases (`r = kB, c = H(m||r||A||B), s = k − ca`); str4d noted it is not DV under Saeednia03 (transcripts become verifiable after key compromise).

### 2. The author's own follow-up framing: zcash/zcash issue #6756 (Sep 8, 2023)
https://github.com/zcash/zcash/issues/6756 — "Identify options for transaction discovery that do not require Θ(#transactions × #wallets) effort" (opened by defuse). Key content:

- Defuse classifies the options: (1) out-of-band transmission ("Liberated Payments", now **ZIP 324 URI-Encapsulated Payments**, draft, https://zips.z.cash/zip-0324, tracking issue https://github.com/zcash/zips/issues/421) through chat apps or a mixnet; (2) transaction tags with an index — linking *his* March 2023 sketch ("allows for efficient lookup at the cost of some privacy and relying on trusted servers acting like a proto-mixnet") and **Arke** (https://eprint.iacr.org/2023/1218, "Arke: Scalable and Byzantine Fault Tolerant Privacy-Preserving Contact Discovery", Mohnblatt/Sonnino/Gurkan/Jovanovic, CCS'24) which "also uses transaction tags, but is much more thoroughly fleshed out … its downside is that recipients need to know senders' addresses in order to do the key exchange to derive the transaction-tag-generating key." Detection keys and TEEs explicitly out of scope (still Θ per wallet).
- **defuse comment, Apr 12, 2024** https://github.com/zcash/zcash/issues/6756#issuecomment-2052528472 — the most important self-critique for our campaign: **the witness-update problem is worse than transaction discovery.** To spend a note the wallet needs its Merkle path, i.e. the sibling note commitment. Either (a) the wallet downloads *all* note commitments (Θ(#transactions) bandwidth, private), or (b) it doesn't, and "the server observing these downloads *can be sure* that the wallet's note is not a sibling of any of the commitments that *weren't* downloaded." Sketched mitigations: random decoy downloads ("privacy properties … would not be that great"), PIR (Θ anyway), second-level indirection proving against an old root inside a tree-of-roots (sender anonymously provides the intra-block path), or "accept the privacy leak and rely on network anonymity (Tor or a mixnet) … however this doesn't really work if the wallet is constantly fetching its t-addr balance" (t-address = identity). **This critique applies verbatim to the March 2023 article's own performance property "the wallet must still update the witnesses for their unspent notes as usual" while fetching only `C^L` ciphertexts from the Detection Server — the article never resolves how witness siblings are obtained privately.**

### 3. Aztec forum, "Note discovery proposal [RFP]" (Jan 19, 2024)
https://forum.aztec.network/t/note-discovery-proposal-rfp/3247 — Janmajayamall's tags + HintlessPIR + bloom-filter proposal (tags `H(x|k)` from a shared secret in a public "handshake tree", single-server PIR via SimplePIR https://eprint.iacr.org/2022/949 and HintlessPIR https://eprint.iacr.org/2023/1733, bloom filter to shrink optimistic tag sets, batch size ~32; concrete cost tables at 10 TPS for 1-hour/1-day/1-week DBs; "tag chaining" variant with key-randomizable ElGamal against identity leakage from `Enc(pk_B, x)`). **earthrise5 (= Taylor Hornby) replies (Jan 22, 2024)** https://forum.aztec.network/t/note-discovery-proposal-rfp/3247/2:
- Critique of the tag approach: every *new* counterparty still forces a trial decryption of the handshake tree; even if 90% of traffic is between established parties, scanning cost drops only ≤10×.
- Restates his own design and concedes its two weaknesses: "generates tags from a symmetric key that's public in the address, and keeps transaction tags private until they've gone through a mixing layer, so that wallets can just look up their tags directly (without PIR) … The drawback is that you would need to get validators to do the mixing in a secure and reliable way, and **the detection server can group ciphertexts by tag to see _how many_ transactions each wallet received**." This is the author confirming the counting/bucket leak is inherent, not incidental.
- Later note in same thread (Aug 30, 2026): poulpy-pir single-server PIR service, https://forum.aztec.network/t/note-discovery-proposal-rfp/3247/5 and https://github.com/poulpy-fhe/poulpy-pir.

## (b) The actual state of Zcash light-wallet detection today (all ZIP numbers verified)

**Detection model: unchanged since 2019 — trial decryption of every shielded output by the wallet itself; privacy model: server is honest-but-curious, detection privacy is NOT achieved against the server.**

- **ZIP 307 — "Light Client Protocol for Payment Detection"** (Status: **Draft**; Owners Jack Grigg, Daira-Emma Hopwood; original author George Tankersley; created 2018-09-17): https://zips.z.cash/zip-0307. Defines compact blocks (116 bytes/output: cmu, epk, first 52 bytes of ciphertext; nullifiers only from spends), trial decryption with `ivk`, incremental witness maintenance, the `CompactTxStreamer` gRPC service, and the honest-but-curious security model ("payment detection privacy" is the *goal*, but the specified mechanism against the proxy is only "download extra decoy full transactions / whole blocks" — §Transaction privacy). §"Block privacy via bucketing" is explicitly "a proposed enhancement that has not been implemented". This is still the only light-client protocol ZIP.

## (c) Related-work attack catalog (what the literature says can break designs of this shape)

### Mixnets: blending / (n−1) attacks — directly applicable to "Mix Authorities"
- **Serjantov & Danezis, "From a Trickle to a Flood" (WPES 2002)** — https://www.freehaven.net/doc/batching-taxonomy/taxonomy.pdf — the canonical attack taxonomy. The **(n−1) attack**: adversary delays the target message, floods a threshold mix with n−1 of their own (recognizable) messages, mix fires, target's recipient is certain. Threshold and timed mixes: attack **exact and certain** (anonymity 0, cost ≈ n−1 messages / ≤2t time). Pool mixes (keep f of n+f): attack becomes *uncertain* and costlier — worked example (n=100, f=60): ~5 rounds / ~500 attacker messages to flush honest messages with >50% success; 99% after 9 rounds. Timed dynamic-pool ("Cottrell", Mixmaster) best practical compromise. **Hornby's Mix Authority is a per-epoch batch shuffle with sort+dedup, i.e., closer to a threshold batch: if an adversary can dominate an epoch's pre-mix input (flood own `C^PrM`), the honest anonymity set within that epoch shrinks to the epoch's honest output count; unlike a classic mix the adversary *cannot delete* other on-chain ciphertexts (they're all in the epoch list), which is the design's main structural defense — but that defense only gives anonymity = (honest outputs in epoch), which spam dilutes cheaply since each attacker output costs only a tx fee.**
- **Danezis & Sassaman, "Heartbeat Traffic to Counter (n-1) Attacks" (WPES 2003)** — https://dl.acm.org/doi/pdf/10.1145/1005140.1005154 — mixes self-probe with anonymous loops (red/green/black traffic) to *detect* blending attacks and inject compensating dummies. (Loopix's `λ_L` loop traffic descends from this.)
- **"On blending attacks for mixes with memory" (Information Hiding 2005)** — https://dl.acm.org/doi/10.1007/11558859_4 — exact round-count analysis of (n−1) attacks on pool / timed-pool / timed-dynamic-pool / binomial mixes.
- **Danezis, "Taxonomy of Mixes and Dummy Traffic"** — https://www.freehaven.net/anonbib/cache/taxonomy-dummy.pdf — mixes without pools are trivially n−1-attackable; **constant-rate dummy policies do not change blending-attack properties** (only scale them); variable (geometric) dummies needed. Relevant to Hornby's optional "R + F dummy self-transactions" obfuscation: constant/simple dummy schedules are exactly the weak case.
- **Replay/tagging countermeasures precedent**: the article's sort+**dedup** (anti "tagging by repeating a unique number of times") and `"mix"||e` associated data (anti cross-epoch replay) mirror Mixmaster/Mixminion replay-handling; Mixminion's link-encryption rationale is in the Loopix related-work (https://arxiv.org/abs/1703.00536, §1/ref [14]).

### Loopix specifically
- **Piotrowska et al., "The Loopix Anonymity System" (USENIX Security 2017)** — https://www.usenix.org/conference/usenixsecurity17/technical-sessions/presentation/piotrowska, extended: https://arxiv.org/abs/1703.00536 — Poisson (exponential-delay) mixing, Sphinx packets, stratified topology, loop (`λ_L`) and drop (`λ_D`) cover traffic, providers with padded inbox pulls (constant message count per pull → receiver unobservability against network observers). **Known gap, stated in the paper (§4.1.2): against a *dishonest provider* "further statistical attacks may be possible, and we leave quantifying exact security against this threat model as future work."** A Detection Server with a known address is precisely a dishonest-provider-plus-known-target scenario. The paper also flags statistical disclosure attacks and reply-message analysis as future work, and relies on senders knowing the recipient's provider — the exact limitation Hornby's article cites when claiming better receiver privacy than Loopix.
- **Statistical disclosure / intersection attacks**: Danezis, "Statistical Disclosure Attacks" (2003) — referenced as [12] in the Loopix paper above; repeated rounds of "user talks to a fixed contact set" inference erode cover traffic over time — the standard attack on any `R + F` self-transaction obfuscation sustained across epochs.
- **Timing attacks on delay-based mixing**: Danezis, "The Traffic Analysis of Continuous-Time Mixes" (PET 2004) — Loopix ref [13] (https://arxiv.org/abs/1703.00536 references section) — mean-tracking attacks defeat stop-and-go/exponential delays when the adversary observes both ends.
- **MixFlow (eprint 2023/199)** — https://eprint.iacr.org/2023/199 — modern confirmation: a contrastive (deep-learning) model links entry/exit flows through Loopix *even as Poisson delay and cover traffic are increased*, from network-edge observation only. Directly undermines any claim that padded/scheduled channels (including Hornby's "constant-bandwidth protocol" for `C^L` delivery and per-Tor-circuit tag lookups) resist determined correlation.
- **Echomix (2025)** — https://arxiv.org/html/2501.02933v2 — notes that per-hop traffic observability still defeats naive padding assumptions (signal-processing analysis "could easily do away with it").

### Tag/bucket notification schemes — count attacks and key-theft persistence
- **Hornby's own concessions (article, "Security Analysis")**: (i) a Detection Server that knows an address "can send many transactions to the known address and watch which 'bucket' grows" — i.e., **bucket-inflation/counting attack is inherent to any tag-indexed bucketing**, acknowledged for "any design that allows the Detection Server to 'bucket' transactions"; (ii) address-knowledge + DS ⇒ user identification by IP (DoS-vs-download trilemma, stated as an open question: "Can we prove that this limitation applies to all possible protocols?"); (iii) DS compromise ⇒ per-epoch received-counts; (iv) one Mix Authority + one DS compromise ⇒ full transaction-to-wallet linkage; (v) no post-quantum privacy (quantum attacker ≡ all-servers-compromised, strictly weaker than Zcash today).
- **FMD — Beck, Len, Miers, Green, "Fuzzy Message Detection" (CCS 2021)** — https://eprint.iacr.org/2021/089 — outsourced detection with tunable false positives. Establishes the privacy/efficiency frontier for detection-key outsourcing; its known limitation (persistent detection capability once the detection key leaks) is exactly earthrise's critique at https://forum.zcashcommunity.com/t/improving-ux-with-detection-keys/46372/30 ("break in once, steal the detection keys, … forever") — the same persistence applies to Hornby's non-indexed path, where the wallet hands `dsk + PRF^D(K_TT, e)` to a new Detection Server.
- **Multi-server FMD — Goes, Khalniyazova, Larraia, Song (Heliax), eprint 2025/2072 (Nov 2025)** — https://eprint.iacr.org/2025/2072 — extends FMD to multiple servers with different detection keys from one secret key, combining high server-side false-positive rates with low receiver-side rates; formalizes "stealth public keys". Its related-work section independently characterizes the Zcash light client ("uses a proxy that retrieves shielded transactions … does not avoid trial-decryption"), in-device smart scanning, Aztec's batch-PIR proposal, and TEE-based approaches [refs 7, 15, 19, 31, 32 therein].
- **Arke (CCS 2024)** — https://eprint.iacr.org/2023/1218 — identity-based non-interactive key exchange handshakes for contact discovery; unlinkability + enumeration-attack resistance + performance independent of user count; the "thoroughly fleshed-out" tag design per Hornby (https://github.com/zcash/zcash/issues/6756), at the cost of requiring recipient knowledge of sender keys.

### PIR-based light clients (and why the article's 2021 PIR critique still stands)
- Qin, Hadass, Gervais, Reardon, "Applying Private Information Retrieval to Lightweight Bitcoin Clients" (IEEE CVCBT 2019) — https://doi.org/10.1109/cvcbt.2019.00012 — PIR-SPV: worst case 100 tx/week queries cost 33.54 MB and ~4.8 min vs 12.85 MB for Bloom-filter SPV.
- Xie et al., "Private Transaction Retrieval for Lightweight Bitcoin Client" (IEEE ICBC 2019; extended in IEEE TSC 2023) — https://doi.org/10.1109/bloc.2019.8751352 — two-step PIR. Ethereum variant: https://doi.org/10.1109/iccchina.2019.8855900.
- PIR-TEE (MSN 2024) — https://doi.org/10.1109/msn63567.2024.00064 — PIR + TEE hybrid for light clients.
- SimplePIR — https://eprint.iacr.org/2022/949; HintlessPIR — https://eprint.iacr.org/2023/1733 — the machinery behind Aztec's RFP numbers (https://forum.aztec.network/t/note-discovery-proposal-rfp/3247). OMR (Oblivious Message Retrieval) — https://eprint.iacr.org/2021/1256, discussed for Zcash at https://forum.zcashcommunity.com/t/oblivious-message-retrieval/40715.
- SoK: Blockchain Light Clients — https://eprint.iacr.org/2021/1657 — systematization incl. privacy assumptions of server-assisted light clients.
- **No PIR light-client design named "Cinder" was found** (searched "Cinder PIR light client blockchain"; no such paper/project exists under that name as of this research). Hornby's own PIR critique (huge queries; **query-count confirmation attack**: probe a guessed address with 1,2,3… payments and watch the victim's PIR-query counts) is at https://forum.zcashcommunity.com/t/zip-314-privacy-upgrades-to-the-zcash-light-client-protocol/38868.
- Set-reconciliation (Erlay) — Naumenko, Maxwell, Wuille, Fedorova, Beschastnikh (CCS 2019) — https://arxiv.org/abs/1905.10518 (PDF: https://www.cs.ubc.ca/~bestchai/papers/ccs19-erlay.pdf; BIP 330: https://bitcoin.org/bip/330/) — bandwidth for tx *relay* via PinSketch/minisketch sketches; a transport-bandwidth technique, not a detection-privacy mechanism; noted to slightly harden tx-origin detection but not solve it.

### Traffic analysis of padded/anonymized channels — the empirical Zcash⇄Nym record (2024–2026)
- Nym×Zcash threat model & hybrid recommendation — https://zcash-sdk.nym.com/ (per-app hybrid: dVPN for block sync + mixnet for broadcast).
- **lwd-mixnet-proxy thread (Aug 2026)** — https://forum.zcashcommunity.com/t/lwd-mixnet-proxy-light-wallet-grpc-over-the-nym-mixnet-and-what-three-days-of-measuring-it-found/57000 — three-plus days of measured gRPC-over-Nym: connected client emits ~**2 Mbps continuous cover traffic**; silent first-payload stream failures ranged **2%–51% across afternoons** (and 60% on a third-party gateway), driving probe/hedge/watchdog machinery (https://github.com/jpgonzalezra/lwd-mixnet-proxy); Nym's harryhalpin: internal packet loss ~20% (target 10%) — https://forum.zcashcommunity.com/t/lwd-mixnet-proxy-...-found/57000/9; a **dead gateway is indistinguishable from bad mixnet weather** to callers (posts 14–16); operational rule: "**don't sync and submit through the same server**" — a sync followed minutes later by an anonymous submission re-links by timing alone (post 1 & 10); Nozy wallet already ships the hybrid (dVPN sync + mixnet `sendrawtransaction`, posts 2 & 12). Implication for the proposal: real mixnet-backed channels are expensive, fragile, and still timing-sensitive — the "Mix Authority must be online 1-of-N" and constant-bandwidth delivery assumptions inherit all of this.

## Implications for our attack campaign (where the gaps are)

1. **Nobody has publicly attacked this design.** The only "breaks" in the literature neighborhood are gtank's 2019 static-derivability attack (already defended against via `K_TT = H(s)` + epoch + hidden `G_r`) and the author's own concessions. Anything we produce beyond (a) bucket-inflation/counting, (b) DS+MA collusion, (c) PQ collapse, (d) known-address DoS trilemma — all author-acknowledged — is novel.
2. **Witness-update hole (strongest angle):** the article's performance-optimized wallet fetches only `C^L` per tag but "must still update the witnesses … as usual"; Hornby's own Apr 2024 analysis (https://github.com/zcash/zcash/issues/6756#issuecomment-2052528472) proves any non-complete commitment download leaks *exclusion* information ("the wallet's note is not a sibling of any commitment not downloaded"). The 2023 design never specifies a private witness mechanism — attack surface: sibling-download pattern vs `GetSubtreeRoots`-style server, even with tags doing their job perfectly.
3. **Epoch-shape attacks:** Mix Authority = per-epoch threshold-style batch shuffle (sort+dedup) → blending-attack math applies (https://www.freehaven.net/doc/batching-taxonomy/taxonomy.pdf): attacker flooding the epoch with own outputs dilutes the honest anonymity set at one fee per output; constant-time-sort caveat is author-admitted; `"mix"||e` + dedup already handle the naive replay/dupe-tag vectors — don't waste effort there.
4. **Count-obfuscation claims are fragile:** `R + F` dummy self-transactions = cover traffic against a dishonest-provider-style adversary — exactly the case Loopix explicitly left open (https://arxiv.org/abs/1703.00536 §4.1.2) and MixFlow defeats empirically (https://eprint.iacr.org/2023/199); intersection/SDA across epochs erodes it further (Danezis 2003 via Loopix refs).
5. **Delivery-channel assumptions:** "constant-bandwidth protocol (fixed-size packets at regular intervals)" for `C^L` delivery is contradicted by the measured Nym experience (2 Mbps cover cost, 2–51% silent failures, timing re-link rule) — https://forum.zcashcommunity.com/t/lwd-mixnet-proxy-...-found/57000.
6. **Key-persistence angle:** non-indexed path hands `dsk + PRF^D(K_TT,e)` to a substitute Detection Server; FMD literature + earthrise's own critique (forum 46372/30) frame the steal-once-detect-forever property — granular per-epoch, but counts for the leaked epoch are permanently recoverable and cross-epoch group linkage survives if addresses leak.
